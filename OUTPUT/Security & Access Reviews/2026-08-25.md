## Proposed resolutions — none executed

### P1 · The orphan credential (Finding 10)

`google_accounts_details.md` records `Personal_client_secret_2_…json` (project `hermes-personal-access-504417`) as unused and "flagged for Eikko to confirm it's safe to delete," dated 2026-08-13. Twelve days on, that flag is unresolved and the file's status here is unverifiable.

**Proposed — Eikko runs on his own machine:**
1. Run the orphan cross-match in the register. Confirm no token carries that `client_id`.
2. If orphaned: **do not delete yet.** Move it out of `OAuth Credentials/` to a local path outside the repo, and confirm all four accounts still authorize.
3. Delete only after that, and record the date in the register.

**Why not delete outright:** a `client_secret` matched by no *local* token can still back a live authorization elsewhere. Deleting it revokes nothing but destroys the ability to refresh. The reversible step costs one move.

### P2 · The 12-day stale verification (Finding 11)

Nothing has verifiably read those four inboxes since 2026-08-13. If refresh tokens are present they self-renew and all is well — but that "if" is the whole question, and no document answers it.

**Proposed:**
1. Run the scopes/expiry loop from the register — confirms refresh tokens exist without printing one.
2. Run one live read per account: `gmail_client.py <key> list-unread`, all four keys.
3. Record the **date and the command** in the register. Not a ✅.
4. Re-verify on a 30-day cycle — the `cio` session opener checks this, deliberately **without** a scheduled task (see P6).

### P3 · Penji connection (Finding 12)

The native claude.ai Gmail connector is already spent on `yeikkomae@gmail.com`, so both Penji inboxes need the custom OAuth script — a `client_secret` per account, then `gmail_auth.py`.

**Blocked before any of that: nobody has written down what the two Penji addresses are.**

**Proposed:** Eikko supplies both addresses → register rows created → then decide whether OAuth is even wanted, given the inboxes are **client-owned**. Connecting a client's inbox to Eikko's tooling is the client's call, not a config step. Worth asking Penji before building it.

### P4 · Repository visibility (Finding 3) — resolved

Verified private, 0 forks. **This is no longer a blocker**, and `OUTPUT/Conversations/` may take real client threads.

**Proposed follow-up, small:** enumerate collaborators and confirm who can reach the six per-client branches (Finding 6). Private-to-the-world is not the same as private-to-a-known-list.

### P5 · The three unexamined tracked files (Finding 5)

`Premium Inboxes.csv` was gitignored for holding 50 mailbox passwords. Three sibling files in the same folder are **tracked**, and no one has checked whether they carry the same kind of content. `Microsoft Office 365.csv` and `GoDaddy.csv` are exactly the shape of file that does.

**Proposed:** Eikko opens all three and checks for a password/secret column. If any carries credentials: add to `.gitignore`, and — because they are already **in git history** — treat rotation of those mailbox passwords as the real remedy. A `.gitignore` addition does not remove what is already committed.

This is the highest-value item in this report, because it is the only finding where a secret may already be in history.

### P6 · No scheduled task — deliberate

`cio` creates no recurring job, and this report proposes none.

Access decay is silent, and the instinct is to automate the check. But an unmonitored automation that stops running looks *exactly* like one with nothing to report — which is the failure mode already in evidence here: two documents assert a connected state that a one-line `grep` disproves. Adding an unwatched job to fix silent decay reproduces the trap.

**Proposed instead:** the 3-line drift check at the top of every `cio` session. It runs when someone is present to read it.

### P7 · The three missing documents (Findings 7–9)

The PRD, `cto.md`, and the reconciliation doc do not exist. `cio` was built from the task description, with the tool-verdict boundary written as a **forward reference** rather than a claim about a live agent.

**Proposed:** if a `cto` is built, revisit `cio.md`'s scope section and make that boundary concrete. Until then it says plainly that no `cto` exists.
